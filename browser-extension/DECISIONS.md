# browser-extension — decisions

Choices made where `docs/design/browser-extension.md` was silent or where the environment forced a
different implementation. Contract problems are in `CONTRACT_ISSUES.md`.

| # | Decision | Why |
| --- | --- | --- |
| D1 | **Validators are precompiled at build time** (`scripts/gen-validators.ts` → `src/generated/validators.js`, Ajv standalone) from the frozen schemas instead of calling `@dome/protocol`'s `schemas.validateBridgeFrame` at runtime. The shipped worker imports nothing from `@dome/protocol` (types only). | Ajv compiles with `new Function`, which the MV3 extension CSP forbids (`unsafe-eval` is never allowed). `test/frames.test.ts` cross-checks the generated validators against the shared library; `test/generated.test.ts` fails on drift. See CONTRACT_ISSUES.md #1. |
| D2 | `permissions` = `nativeMessaging`, `storage`, `alarms` (the design's manifest listed two but its text relies on `chrome.alarms`), and since D26 `scripting`; `content_security_policy.extension_pages` is set explicitly to `script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'`. | Spec §15 asks for a restrictive CSP; it only tightens Chrome's default. `scripting` only runs the extension's own `content.js`, and only where the single YouTube host permission allows it. No other manifest additions. |
| D3 | Tabs without a running content script refuse ops with **`TAB_NOT_CONTROLLABLE`** (not `UNSUPPORTED_CONTEXT` as one bullet of the design says). | `errors.json` has `TAB_NOT_CONTROLLABLE` with exactly the "reload the YouTube tab" copy, the bridge schema and the agent's fake extension use it, and the design's own first bullet says so. |
| D4 | A clicked Next/Previous whose transition is **not observed** before the deadline is reported as `OUTCOME_UNKNOWN` ("may or may not have happened"); `NO_NEXT_VIDEO` is used only when the button is absent/disabled/hidden, `TARGET_CHANGED` when `expected_video_id` no longer matches. | The design says "else NO_NEXT_VIDEO / TARGET_CHANGED" but a click that happened without observable effect is neither; the spec forbids auto-repeat after ambiguous timeouts, so the honest code is the one the phone already treats as "retry with warning". See CONTRACT_ISSUES.md #2. |
| D5 | Content-script replies that arrive after the background's own deadline: `OUTCOME_UNKNOWN` for mutating ops, `TAB_NOT_CONTROLLABLE` for `get_state`. The content script gets `deadline_ms = timeout_ms − 700` so it normally answers first. | Same reasoning as D4; the agent maps *its* timeout to `EXTENSION_DISCONNECTED`, which would be misleading for a tab-local hang. |
| D6 | The content script does **not** import `@dome/protocol` or the generated validators; it only exchanges small internal messages with the worker, which sanitizes (`sanitizeSnapshot`) and validates (`validateYoutubeTab`) everything before it becomes a contract frame. | Keeps `content.js` at ~23 KB with zero dependencies on every YouTube page, and keeps a single validation point at the real trust boundary (the native port). |
| D7 | Reconnect backoff 1, 2, 4, 8 s, then every 8 s, for a **fast window** of 5 minutes from the first failure (at most 40 attempts); after that every 30 s through `chrome.alarms` alone. Fast delays use `setTimeout` *and* a 30 s `chrome.alarms` safety net; after `PROTOCOL_INCOMPATIBLE` the retry is every 5 min (alarm only). A new window opens on browser start (`onStartup`), install/update/reload (`onInstalled`), the popup's Retry and every ack (so losing an acknowledged agent is fast again). The window's end is kept in `chrome.storage.session`: a worker woken by the slow alarm stays slow, while a browser restart or an extension reload, update or disable clears it. `connect()` is idempotent. Deviates from the design's 1→60 s. | On the owner's PC the browser (and the extension) usually starts before DoMe — the test kit even loads the extension before starting the agent — and with a 60 s cap a freshly started agent stayed unfound for up to a minute; the 8 s cap keeps that under ~10 s. Every attempt while the agent is down starts a Python native host (KNOWN_ISSUES K5), and without a limit that ran every 8 s for as long as the browser was open, once per browser; a pending timer or an open port also kept the worker from sleeping. After 5 minutes a late agent is found within 30 s, or at once with Retry. `chrome.alarms` cannot fire sooner than 30 s (Chrome 120+) but is the only timer that survives worker termination; together the extension is never left unrecoverable. |
| D8 | Version check in both directions: the extension refuses a `bridge_hello_ack.protocol_version` outside its supported list with `bridge_error{PROTOCOL_INCOMPATIBLE, detail:{peer, supported}}` and closes the port. `protocolCompatible` is re-implemented (10 lines) in `src/shared/version.ts` with a parity test against `@dome/protocol`. The supported list is `["1.0", "1.1"]` — every MINOR the extension speaks, not only the newest. | The worker cannot import `@dome/protocol` (D1); the agent does the same check on its side. 1.1 (manual input) left `bridge.schema.json` unchanged, so the extension speaks it as-is; listing only `1.0` made it refuse the 1.1 agent's ack, so no YouTube control could work. Listing every MINOR keeps older agents accepting a newer extension. A higher MINOR is added only once the extension implements what it changed in the bridge. |
| D9 | `player_state` events are throttled twice: 500 ms in the content script (leading + trailing) and 500 ms per tab in the worker. `timeupdate` only refreshes position every 5 s. `tabs_changed` is debounced 300 ms and always carries the full list. | Contract: ≤ 2 per second per tab; the agent *replaces* its tab map with each `tabs_changed`. |
| D10 | `list_tabs` probes every YouTube tab (2 s timeout) for fresh state; the worker also probes all tabs on start to rebuild the cache after termination. A tab that does not answer is reported `script_attached:false`. | Design: the cache is rebuilt from `tabs_changed` + fresh `get_state` after a worker restart; a tab that cannot answer a probe cannot execute an op either. |
| D11 | `set_muted` clicks YouTube's `.ytp-mute-button` first (when `video.muted` differs from the request) and falls back to `video.muted = …`; `set_volume` writes `video.volume` directly and never changes `muted`. | The button keeps YouTube's UI consistent and is an absolute operation given `video.muted`; there is no YouTube control for an absolute volume value, and mute/volume are separate controls in the spec. Manual item in README. |
| D12 | Context gating in the content script: ad showing → only `get_state`/`set_paused`/`set_muted`/`set_volume`; Shorts → no `next`/`previous`/`set_theater`; live → no seeking; `context:"other"` (no player) → no control ops. Live streams may still receive `next`. | Design table + "no ad bypass". Seeking on live DVR is deliberately left out of launch scope. |
| D13 | `request_fullscreen` targets the `.html5-video-player` container; any rejection is `ACTIVATION_REQUIRED` with the DOM error name in the message. | Spec §9: report the activation restriction honestly, never a shortcut workaround. |
| D14 | Popup = status, troubleshooting hints, `profile_label` (re-sends `bridge_hello`, which the agent accepts) and a "Retry connection" button; no playback controls. The title says in plain words whether it works and what to do (*Connected*, *Connecting...*, *Not connected - start DoMe on this PC*, …; `src/popup/status.ts`), the hint gives the next step, and the browser's or agent's own message is shown below as *Details: …*. **Retry connection** drops anything the agent has not acknowledged (an unanswered hello, a port the host left open, a pending backoff) and connects at once with a fresh backoff and a new fast-retry window (D7); it does nothing while connected. | Task: "popup (status only)"; design: `profile_label` is user-settable in the popup. The owner is not technical: state names such as *host_missing* or *agent is not running* did not tell him what to do. Retry used to be a no-op whenever the extension still believed it was connected. |
| D15 | Message authentication inside the extension: the worker accepts content messages only from `sender.id === chrome.runtime.id`, top frame (`frameId === 0`) and a `https://www.youtube.com/` URL; the content script accepts ops only from the extension (no `sender.tab`). The manifest has no `externally_connectable`. | Pages cannot message the extension, but the checks make that explicit and testable. |
| D16 | Build: three Vite invocations (module worker, IIFE content script, popup HTML) into one `dist/`; no minification; no icons yet (Chrome shows a default). | Content scripts cannot be ES modules; separate builds avoid shared chunks. Unminified output stays reviewable for store review and support. |
| D17 | Logging: `src/shared/log.ts` only accepts scalar fields; request ids, tab ids, codes, counts and `browser_instance_id` are logged, never titles, tokens, URLs or frames. | Spec §15. |
| D18 | **`tabs.onUpdated` never deletes an attachment on `status:"loading"`/`"complete"`.** Chrome reports those for `history.pushState` too, i.e. for every in-site YouTube navigation (related video, the player's Next, playlist advance), during which the content script stays alive with the same `tab_token`. The content script's `attached`/`detached` messages remain the authority; on `loading`/`complete` the worker only sends a cheap probe and drops the attachment when nobody answers (`NoReceiverError`/timeout) — that covers a full reload whose `detached` message was lost. Only `discarded:true`, `onRemoved` and `onReplaced` delete directly. | Review finding: the old deletion made every SPA navigation flicker to `script_attached:false` and could turn an observed, successful `next` into `TARGET_GONE` (spec §9 forbids inaccurate Next reporting). |
| D19 | After a tab op, the result is composed from the attachment **just recorded from the content script's reply** (`composeById(tabId, attachment)`), never from a cache re-read after an `await`. A reply that claims success without a usable state is `INTERNAL`; `TARGET_GONE` after a reply only when the tab really closed or left YouTube. | Same finding: a tab event dispatched between `record()` and `compose()` must not change the outcome of an action that was observed to succeed. |
| D20 | **Hello-ack deadline of 10 s** (`HELLO_ACK_TIMEOUT_MS`): a native host that opens the port but never sends `bridge_hello_ack` is disconnected, the state becomes `disconnected` ("did not answer the extension's hello") and the normal backoff (D7) applies; the timer is cleared on ack, disconnect and port failure. | An open-but-silent port kept the worker alive, made `connect()` a no-op and the alarm useless, so the extension showed *Connecting…* forever while the agent saw `extension_connected=false`. Only the popup's Retry recovered. |
| D21 | `start()` runs `registry.rebuild()` **before** `connection.connect()`, and `rebuild()` always triggers the (debounced) `tabs_changed` when it finishes. | The `tabs_changed` sent on the ack must be built from a complete cache; when `connect()` was started independently (`onStartup`, `onInstalled`, alarm) and acknowledged mid-rebuild, the trailing `tabs_changed` corrects the earlier one instead of leaving the agent with stale `script_attached:false` entries. |
| D22 | **Time budget floor.** `timeout_ms` (schema minimum 100) is floored to 1000 ms: the background waits `budget − 200` and hands the content script `deadline_ms = budget − 700`, so `deadline < background wait` holds for every schema value (`computeBudget`). Values below 1000 are not rejected. | Below ~900 ms the background used to time out before (or at) the content script's deadline, reporting instant `OUTCOME_UNKNOWN`/`TAB_NOT_CONTROLLABLE` on healthy tabs. Rejecting would turn a latent agent-side tuning choice into a hard failure; flooring keeps the semantics D5 relies on. See CONTRACT_ISSUES.md #5. |
| D23 | After an observed `next`/`previous` transition the adapter waits (≤ 1500 ms, never beyond the remaining `deadline_ms`) for the page to **settle** — `yt-navigate-finish`, `yt-page-data-updated`, `loadedmetadata`/`durationchange` on the video, or the heading text changing — before taking the result snapshot. If nothing arrives, the result is still `ok` with the new `video_id`/`previous_video_id` but **omits `title`, `duration_seconds` and `position_seconds`** rather than pairing the new id with the previous video's values. | The transition is observed at the URL change, when YouTube has not yet swapped title/metadata; the phone would otherwise render a mismatched title until the next `player_state`. Position is omitted along with title/duration because it describes the previous media just as much. |
| D24 | Live detection: `is_live` is true only when `.ytp-time-display` carries `.ytp-live`, the `.ytp-live-badge` is actually rendered (computed `display` not `none`, not disabled), or `video.duration === Infinity`. Bare presence of `.ytp-live-badge` is ignored. | YouTube keeps the badge element in the player chrome on every watch page and hides it with CSS on VOD; the old selector would have marked every tab live and refused all seeking. The VOD fixture now carries the hidden badge with the same CSS rule. |
| D25 | **A `bridge_error` `AGENT_DISCONNECTED` or `AGENT_NOT_RUNNING` from the host closes the port at once** (state `disconnected` / `agent_not_running`, normal backoff, D7); `PROTOCOL_INCOMPATIBLE` from the agent closes it too and retries every 5 min. A native-port disconnect for any other reason already did the same. Frames from a port the worker has dropped are ignored. | The native host reports the agent's side ending but can stay alive with the port open (it waits on its stdin); the worker kept the dead port, `connected` still read true, `connect()` was a no-op, and only reloading the extension or restarting the browser recovered after DoMe was restarted. The agent closes its side after refusing a hello, so the host's following `AGENT_DISCONNECTED` must not turn a slow incompatible retry into a fast loop. |
| D26 | **Content script injection into tabs that were already open.** On `runtime.onInstalled` (install, update, reload) and `runtime.onStartup` the worker runs `content.js` in every open, non-discarded YouTube tab with `chrome.scripting.executeScript` (`scripting` permission). Every worker start also probes the open YouTube tabs (`TabRegistry.rebuild`) and runs `content.js`, without waiting for it, in each non-discarded tab that has no content script at all (`NoReceiverError`): that covers the extension being disabled and enabled again (no `onInstalled`/`onStartup`) and a crashed renderer; tabs whose script answers or is only slow are left alone. The content script starts once per page: `startContentScriptOnce` keeps the running instance (marker on its isolated-world global, which page scripts cannot see or set) and replaces only an instance orphaned by an extension reload (`chrome.runtime.id` gone). Failures per tab are logged by error name only. | Chrome injects manifest content scripts only into pages loaded afterwards, so tabs open before the extension was installed or reloaded stayed *reload needed* — the usual case on the owner's PC. Both the manifest and the worker can inject into the same page (a tab loading during install, browser start), so the script must be idempotent: two instances would announce two tokens and answer ops twice. Discarded tabs get the manifest injection when they load again. Disabling the extension cuts off its content scripts, and enabling it fires neither event, so every open YouTube tab stayed *reload needed* — and turning the extension off and on is a usual troubleshooting step. The injection is not awaited so a hung tab cannot delay connecting to the agent. |
