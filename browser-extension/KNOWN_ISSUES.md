# browser-extension — known issues

Open items after the review pass. All blocker/major/minor review findings were fixed (see
`DECISIONS.md` D18–D24 and the tests named below); what remains is residual risk that cannot be
closed without a real browser session.

| # | Issue | Impact | Mitigation / how to verify |
| --- | --- | --- | --- |
| K1 | **Selectors are unverified against youtube.com.** Live detection (D24) relies on `.ytp-time-display.ytp-live`, the rendered state of `.ytp-live-badge`, and `video.duration === Infinity`; title on `h1.ytd-watch-metadata`; settle events `yt-navigate-finish` / `yt-page-data-updated` (D23). The fixtures mirror these but are hand-written. | If YouTube renames a class, `is_live` could be wrong (seek refused or allowed on a live stream) or Next results could lack `title` until the next `player_state`. | README manual checklist items 2 and 4 (VOD page must show `is_live:false` and allow seeking; live page `is_live:true`; Next result shows the **new** title). |
| K2 | **Stale attachment window on a full reload whose `detached` message is lost.** On `status:"loading"` the old document may still answer the verification probe (the navigation has not committed yet), so the registry keeps the old token until the content script's `detached` message, the `status:"complete"` probe, or the next op (`TAB_NOT_CONTROLLABLE`) clears it. | For at most a page load, `tabs_changed` can list a reloading tab as attached with a token that is about to die; an op in that window fails honestly with `TAB_NOT_CONTROLLABLE`/`TARGET_CHANGED`, never acts on the wrong video. | Checklist item 9 (reload → *reload needed* → attached with a new token). Deleting on `loading` is not an option (D18). |
| K3 | **Fixed internal read-back windows are not bounded by `deadline_ms`.** `set_paused` (1 s), `seek` (2 s), `set_muted` (0.8 + 0.5 s), `set_theater` (1.5 s), `request_fullscreen` (1 s) wait their own fixed time; with the 1000 ms budget floor (D22) the background can time out first for those ops when the agent sends a sub-second `timeout_ms`. | Latent: the agent sends 8000/10000 ms. With a tiny timeout a slow player could yield `OUTCOME_UNKNOWN` instead of `ACTION_UNAVAILABLE`. | Bound those waits by `deadline_ms` as well if the agent ever lowers its timeouts; `CONTRACT_ISSUES.md` #5 asks for a schema minimum of 1000. |
| K4 | **Hello-ack timeout state is generic.** After 10 s without `bridge_hello_ack` the popup shows *Not connected - start DoMe on this PC* with *Details: The DoMe agent did not answer the extension's hello*; it cannot tell a stalled native host from a stalled agent IPC (or a stuck Windows named pipe). | Customer sees a retrying state rather than a precise cause. | The host-side log (`dome-native-host`) distinguishes the two; the reconnect loop recovers either way (test: "a host that never acknowledges hello…"). |
| K5 | **Retrying while DoMe is not running starts a native host process every 8 s for about 5 minutes, then every 30 s.** Each attempt makes the browser start `dome-native-host` (Python), which finds no agent, sends `AGENT_NOT_RUNNING`, writes **two** lines to the rotated `native-host.log` (*native host started*, *agent IPC endpoint unavailable*) and exits. The fast pace (1, 2, 4, 8, 8 … s, at most 40 attempts) runs only for about 5 minutes after the browser starts, the extension is installed/reloaded/enabled, an acknowledged connection is lost or Retry is pressed (D7); after that only the 30 s alarm retries, with no timer or open port in the worker. | Measured in review on Linux: about 0.3 s CPU per host start; Python start-up on Windows with Defender scanning is usually slower. The fast window costs roughly 40 starts (about 12 s CPU, 80 log lines) per browser. The slow phase costs one start per 30 s: about 1 % of one core on Linux, more on Windows, and about 5,800 log lines (roughly 1 MB) a day per browser, twice that with Chrome and Edge both open. The log is rotated (2 MB × 4 files), so nothing accumulates. An agent started more than 5 minutes after the browser is found within 30 s, not ~10 s. | On the real PC with DoMe stopped and the browser open: Task Manager → Details shows at most one short-lived `dome-native-host.exe`/`python.exe` at a time, about every 8 s for the first 5 minutes and every 30 s after. *Retry connection* in the popup connects at once. Whether Chrome actually stops the idle worker between the 30 s alarms (its idle limit is also 30 s) is **not verified**; the host processes, not the worker, are the cost. |
