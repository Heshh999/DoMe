# brand — contract / shared-library issues

The brand component does not touch `shared/protocol` or the shared libraries, and nothing under
`shared/` was modified. There are no wire-contract issues. Two notes about the builders' brief:

## 1. The brief routes exports through `mobile-app/scripts/make-icons.mjs` and `pc-agent/dome_agent/assets/`

**Brief** (`docs/design/input-control.md` §6): "exports through `mobile-app/scripts/make-icons.mjs`
(PWA icons, favicon) and PNGs for the Windows tray/installer in `pc-agent/dome_agent/assets/`".

**Task rule**: write only under `brand/`; do not modify `mobile-app` or `pc-agent`; the maintainer
wires the exports in.

**Resolution**: the exports are generated by `brand/scripts/export.mjs` into `brand/exports/`
(DECISIONS D2, D8). The mobile-app side is wired: `mobile-app/scripts/make-icons.mjs` now reads
`brand/exports/manifest.json` (`file`, `source`; it requires `source: "icon.svg"`) and copies
`pwa/icon-192.png`, `pwa/icon-512.png`, `pwa/icon-192-maskable.png`, `pwa/icon-512-maskable.png`,
`pwa/apple-touch-icon-180.png`, `favicon/favicon-16.png`, `favicon/favicon-32.png`,
`favicon/favicon.ico` and `icon.svg` (as `favicon.svg`) into `mobile-app/public/icons/`. Those export
paths and manifest fields are therefore an interface: renaming one must be done together with that
script (`tests/brand.test.mjs` fails if the script asks for a path the plan no longer produces).
Still pending: `pc-agent/dome_agent/assets/` does not exist, `pc-agent/dome_agent/tray.py` draws its
own shape and `pc-agent/packaging/*.spec` have `icon=None`; BRAND.md §7 lists the files to use
(`windows/tray-*.png` for the tray, `windows/dome.ico` for `icon=`).

## 2. No image library is available in the repository's toolchain

Not a contract issue but worth recording for whoever wires the assets: `mobile-app/node_modules`
contains no `sharp`/`resvg`, and the machine used for this build has no SVG rasterizer at all, which
is why `brand/scripts/export.mjs` carries its own (README "How the exports are made"). If the
maintainer later adds a rasterizer to the toolchain, the SVG sources are standard and will render
unchanged; the subset restrictions exist only so that the self-contained script stays correct.
